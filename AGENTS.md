# AGENTS.md - Swift/SwiftUI/XcodeGen over a Rust bridge

## Scope
Applies to this repo unless a deeper `AGENTS.md` overrides it.
`docs/ideas/`, `docs/plans/`, and `docs/reviews/` have their own
`AGENTS.md` contracts. Follow explicit user instructions first.

## Parity with Android
This app is the iOS twin of `../passalong-android`
(`joelee/passalong-android`). Features, wording, status messages, config
format, and on-disk layout follow the Android app and, through it, the
passalong CLI; a deliberate difference is an iOS platform constraint and is
recorded in `docs/architecture.md`. When the Android app gains a feature,
its iOS counterpart goes into `docs/backlog.md`.

## Stack
- Swift 6 and SwiftUI, iOS 17+ (`@Observable`, `NavigationStack`); one app
  target until that hurts. The Xcode project is generated by XcodeGen from
  `project.yml`; the generated `.xcodeproj` is never committed or
  hand-edited.
- Platform-free logic (domain, the `Core`/`StoreHandle` protocols, data,
  the setup and choose controllers) lives in the local Swift package
  `PassalongKit/`, Foundation only, so it tests with `swift test`.
- Storage, SSH, host-key pinning, the item schema, verification, and
  encryption come from the Rust core: `rust/` holds `passalong-ffi`, a
  UniFFI bridge over `passalong-core`, `passalong-ssh`, and
  `passalong-https`, pinned exactly. The app never reimplements store
  logic.
- Swift touches the generated bindings only in `App/Core/FfiCore.swift`;
  everything else depends on the `Core` and `StoreHandle` protocols.
- `scripts/rust-ios.sh` builds the library for `aarch64-apple-ios` and
  `aarch64-apple-ios-sim`, generates the Swift bindings with the crate's
  own `uniffi-bindgen` binary, and packs `PassalongFFI.xcframework`; the
  Xcode build runs it as a pre-build script. Commit `rust/Cargo.lock`.
- Format Swift with `swift format` (the toolchain's swift-format) and Rust
  with rustfmt; lint with SwiftLint and clippy.
- Builds, Simulator runs, signing, and coverage need macOS with Xcode;
  the Rust bridge's host tests also run on Linux.

## Non-negotiables
- TDD: write or update a failing unit test before production code; then
  implement; then refactor.
- Unit tests (Swift Testing) mock external interfaces: the core (`Core`,
  `StoreHandle`), the pasteboard, the files sink, the filesystem, and
  time. The Rust bridge is tested on the host with `cargo test` over the
  `local` backend.
- Every feature includes integration-test coverage planned up front and
  implemented before completion.
- Coverage gate: Swift line coverage >= 80 % (`just coverage`), measured
  over `PassalongKit`; the generated bindings, `FfiCore`, the sinks, and
  the SwiftUI views in `App/` are excluded because only Simulator tests
  can run them. Report coverage in completion notes.
- DocC comments (`///`) for public APIs and non-obvious logic; rustdoc
  likewise; avoid comments that restate code.
- Avoid `unsafe` in Rust; any exception carries a safety comment and is
  named here.
- Swift 6 strict concurrency: no `@unchecked Sendable` or
  `nonisolated(unsafe)` without a comment saying why it is sound.
- No secrets in code, tests, docs, logs, or VCS.

## Commands
Use these unless project docs define stricter commands:
- Format: `just fmt`; check: `just fmt-check`
- Lint: `just lint`
- Tests: `just test`
- Coverage: `just coverage`
- Build: `just build` (Simulator debug build, builds the Rust library first)
- All checks: `just check` (fmt-check, lint, test, coverage, build)
- Pre-commit must enforce the same checks; keep `.pre-commit-config.yaml`
  current and verify with `pre-commit run --all-files` when installed.

## Config and secrets
- The device's config is the core's `config.toml`, written by the setup
  screen into the app's Application Support directory; the identity key,
  the API key file, and the list cache live beside it, excluded from
  iCloud backup. See `docs/configuration.md`.
- The app generates its own passphrase-less ed25519 key; no passphrase is
  ever stored or prompted.
- Signing identities, provisioning profiles, the development team ID
  override (`Local.xcconfig`), and `.env` stay out of VCS (git-ignored).
- Local core hacking uses a git-ignored `rust/.cargo/config.toml` path
  patch toward `../passalong`; never commit it.

## Observability
- The core logs through `tracing`; the bridge sends every record to the
  unified log (subsystem `io.github.joelee.passalong`, category
  `passalong`) with the core's format and levels (`init_logging`). Swift
  logs through `os.Logger` with the same subsystem when it must.
- Never log pasteboard text, file contents, keys, or secrets.

## New feature workflow
1. Run `git status --short`. If non-empty, stop and report dirty files;
   do not edit.
2. Create branch: `git switch -c feature/<feature_name>`.
3. Add a `CHANGELOG.md` entry under `Unreleased`.
4. Create a plan in `docs/plans/` per its `AGENTS.md` contract, allocating
   the number with `.agents/skills/allocating-report-numbers/`.
5. Plan must include scope, TDD unit tests, integration tests,
   config/secrets impact, observability, docs, coverage target, risks, and
   the Android counterpart it matches.
6. Write failing unit tests first; mock external interfaces.
7. Implement minimal code; add integration tests; update docs and backlog.
8. Run `just check` and ensure coverage >= 80 %.
9. Report changed files, tests run, coverage result, docs updated, and
   backlog updates.

## Release workflow
1. SemVer `vMAJOR.MINOR.PATCH`; default PATCH. `MARKETING_VERSION` follows
   the tag; `CURRENT_PROJECT_VERSION` increases by one per release.
2. All checks pass, coverage >= 80 %, branch CI passes; agent hands off
   with the evidence; user reviews and approves.
3. One finalising commit `release: vX.Y.Z - <top feature>`: rename
   `Unreleased` in `CHANGELOG.md`, bump the version settings in
   `project.yml`, refresh the release notes.
4. Signing lives outside VCS; the user archives and signs the build. The
   pipeline (TestFlight, App Store, or ad hoc) is defined in a release plan
   before the first release.
